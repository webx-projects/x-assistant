# Architecture

## Direction

The Android client follows Clean Architecture with MVVM and feature-oriented packages. Dependencies point inward: presentation depends on domain contracts; data implements domain contracts. Domain code must not depend on Android UI or network libraries.

## Local data model (database v1)

Room is the primary source of truth. The first schema contains:
- Tasks, with status, priority and optional due date.
- Financial transactions, with explicit income/expense type and integer minor-unit amounts (paise for INR).
- Reminders, with scheduled timestamp and an optional recurrence rule to be validated by the domain layer.
- Notes, with title, body and pin state.

DAOs expose reactive Kotlin Flow queries. Finance summaries are calculated over integer minor units and formatted by application code; the model must never be trusted for arithmetic. IDs are generated by the application layer. New schema changes require explicit Room migrations and updated schema snapshots; destructive migration fallback is not enabled.

## Planned package boundaries

- `core/`: shared design system, navigation, networking, security, date/time and result types.
- `domain/`: business models, repository interfaces and use cases.
- `data/`: Room entities/DAOs, repository implementations, gateway DTOs and mappers.
- `presentation/`: dashboard, assistant conversation and feature screens.

## OmniRoute gateway

The Android client uses the configured gateway host `https://ai.vmstudio.digital`. The public OmniRoute OpenAI-compatible contract documents a `/v1` API root, Bearer-key authentication and `POST /v1/chat/completions` with `model`, `messages` and optional `stream` fields. Model identifiers are gateway-specific; the client currently defaults to `auto`, which must be supported by the deployed instance. The public protocol reference is not proof that this particular hosted instance is reachable or configured identically.

The first client implementation sends non-streaming chat completions. It does not yet execute tool calls. Before production release, verify the deployed host's `GET /v1/models`, key permissions, rate limits, selected model capabilities and error behavior using a real user key. Do not assume every model supports tools or structured output.

API keys are entered by the user and encrypted with an AES-GCM key held in Android Keystore; only ciphertext is stored in app-private preferences. Never commit API tokens, place them in BuildConfig, or embed a shared private credential in the APK. For multi-user production deployment, prefer a controlled backend proxy with per-user authorization and quotas.

## Voice and Android restrictions

Push-to-talk speech recognition and text-to-speech are not implemented yet. Hands-free activation is a later capability gated by Android-supported assistant/hotword APIs and device support. Background microphone use must remain user-visible and comply with foreground-service and permission rules. No hidden recording, root requirement or AccessibilityService workaround.

## Data safety

- Typed tool calls only; no arbitrary SQL, shell or code execution from the model.
- Confirm destructive actions before mutation.
- Verify persisted state before reporting an action as complete.
- Keep optional backup distinct from automatic two-way sync.
- Do not log transcripts, credentials or financial details unnecessarily.
